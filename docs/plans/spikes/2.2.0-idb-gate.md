# Spike verdict — TASK-2.0.1 / VER-003: does idb work on this Xcode?

**Verdict: WORKS**, with three prerequisites that must be documented, and one
tooling incompatibility that has to be worked around.

Run on 2026-08-05.

## Environment

| Component | Version |
| --- | --- |
| macOS | 26.4.1 (arm64) |
| Xcode | 26.1.1 (Homebrew warns it is behind 26.3) |
| Runtime | iOS 26.0 |
| Simulator | iPhone 17 Pro — `AAAAAAAA-1111-2222-3333-BBBBBBBBBBBB` |
| `idb-companion` | 1.1.8 (`brew install facebook/fb/idb-companion`) — build date Aug 2022 |
| `fb-idb` client | 1.1.7 |
| Client interpreter | **Python 3.12.13 (required — see below)** |

## Findings

### F-1 — `fb-idb` 1.1.7 is incompatible with Python 3.14 (blocking)

`pipx` installed the client under the default Homebrew Python 3.14.6, and every
invocation died before doing any work:

```text
File ".../idb/cli/main.py", line 353, in main
    loop = asyncio.get_event_loop()
RuntimeError: There is no current event loop in thread 'MainThread'.
```

`asyncio.get_event_loop()` with no running loop was deprecated in 3.10 and became
a hard error by 3.14. Fix — pin the interpreter:

```bash
pipx reinstall fb-idb --python /opt/homebrew/opt/python@3.12/bin/python3.12
```

This is a documentation and `doctor` concern: a user on a Python-3.14-default
machine will hit it immediately, and the traceback does not suggest the cause.

### F-2 — Homebrew now refuses untrusted taps (blocking)

`brew install idb-companion` fails with *"Refusing to load formula from untrusted
tap facebook/fb"*. Resolved with the narrowest possible grant:

```bash
brew tap facebook/fb
brew trust --formula facebook/fb/idb-companion   # not `brew trust facebook/fb`
brew install idb-companion
```

### F-3 — `idb` has no `--version` flag

`idb --version` exits non-zero with *"unrecognized arguments: --version"*. The
readiness probe now runs `idb list-targets --json`, which exercises client **and**
companion. `idb_companion --version` does work and prints a build date.

### F-4 — `simctl bootstatus -b` exits 0 even when the boot failed

The simulator's data directory had been deleted out from under CoreSimulator.
`bootstatus` printed *"Unable to boot device because it cannot be located on
disk"* and still **returned exit code 0**, leaving the device `Shutdown`.

Trusting that exit code would have made `session start` report a successful boot
against a device that was not running — every later verb would then fail with a
confusing downstream error. `ios_simctl.boot()` now re-queries the device state
after `bootstatus` and only reports success when the state is actually `Booted`.

Recovery for a device in this state: `xcrun simctl erase <udid>`.

### F-5 — private-framework collision warning is cosmetic

```text
objc: Class FBProcess is implemented in both /System/Library/PrivateFrameworks/FrontBoard.framework
and .../idb-companion/1.1.8/Frameworks/FBControlCore.framework
```

Printed on stderr by `idb_companion`; functionality is unaffected. It is a
concrete reminder of why RISK-006 confines idb knowledge to `ios_idb.py`.

## `describe-all` shape — U-001 resolved

**Flat JSON array. No nesting.** One object per accessibility element:

```json
{
  "AXFrame": "{{16, 380.33}, {370, 52}}",
  "AXUniqueId": "com.apple.settings.general",
  "frame": {"y": 380.33333333333337, "x": 16, "width": 370, "height": 52},
  "role_description": null, "AXLabel": "General", "content_required": false,
  "type": "Button", "title": null, "help": null, "custom_actions": [],
  "AXValue": null, "enabled": true, "role": "AXButton", "subrole": null
}
```

Confirmed against the plan's §2.4 mapping table:

| Compact field | Real source | Status |
| --- | --- | --- |
| `desc` | `AXLabel` | confirmed |
| `text` | `AXValue` | confirmed — **null for every element on this screen** (see F-6) |
| `resource_id` | `AXUniqueId` | **confirmed populated** — the plan assumed null on iOS |
| `bounds` | `frame` (floats) | confirmed; truncated to int points |
| `role` | `type` | confirmed; plain names (`Button`, `Heading`, `Group`, `Application`), not `XCUIElementType`-prefixed |
| `enabled` | `enabled` | confirmed |
| `package` | — | **no bundle id on elements**; stays null |
| `clickable` | — | **no `traits` array**; inferred from `type` |

`AXFrame` is a formatted string; `frame` is the structured one. The parser reads
`frame`.

### F-6 — the visible label lands in `desc`, not `text`

Every element on the Settings screen has `AXValue: null`, so the compact `text`
field is null and the label is in `desc`. On Android the same visible label
arrives in `text`. An agent that habitually does `ui find --text "General"` gets
zero matches on iOS and would conclude the control is absent.

The mapping itself is correct and matches the approved spec, so it was left
alone. **This needs a skill-text note in `mobile-screen` (Milestone 2.4): on
iOS, select by `--desc` or `--resource-id`.** A follow-up worth considering is a
warning when `--text` matches nothing but the same string matches a `desc`.

## End-to-end evidence (VER-012 shape, on the real simulator)

| Step | Result |
| --- | --- |
| `devices --platform ios` | `iPhone 17 Pro \| Booted \| iOS 26.0` |
| `session start --platform ios --target <udid>` | `ok`, `schema_version: 2`, `tooling.idb.state: ready` |
| `ui tree` (live) | 14 meaningful nodes of 15 raw; unlabelled `Group` filtered |
| `ui find --desc General --mode exact` | 1 match, `n5`, bounds `[16, 380, 386, 432]`, id `com.apple.settings.general` |
| screenshot before | 399 248 bytes, valid PNG |
| `ui tap --desc General --mode exact` | dispatched `(201, 406)` — points, unscaled |
| screenshot after | 327 229 bytes — **differs from before** |
| `ui tree` after | 12 nodes: `General` heading, `BackButton`, `About`, `Screen Capture`… |
| `logs tail --package com.apple.Preferences` | `ok`, 5 lines, no warnings |
| `session stop` | `ok`, teardown reported per action |

The screenshot diff plus the changed tree are the oracle: the tap did something
real, rather than merely exiting 0.

**Scale check:** the device is 3x Retina. The tap went to `(201, 406)` in points.
A pixel mix-up would have produced `(603, 1218)`, outside the 402×874 point
screen — which the guard now refuses outright.

## Actions taken

1. `ios_simctl.boot()` verifies device state instead of trusting the exit code (F-4).
2. `ios_idb.version()` probes via `list-targets`; added `companion_version()` (F-3).
3. `ROLE_BY_TYPE` extended with the real types (`Heading`, `Group`, `Toolbar`).
4. Provisional fixtures deleted; `tests/fixtures/idb_describe_all_sample.json` is
   now real captured output, with a derived nested variant kept only to prove
   shape tolerance.
