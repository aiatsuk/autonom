# Spike verdict — TASK-3.3.0: how should the iOS Simulator attach to the proxy?

**Verdict: PARTIAL — automated for proxy-env-aware clients, documented manual for
the rest.** This is the outcome DEC-006 pre-committed to, so no re-approval is
needed.

Run on 2026-08-05 against macOS 26.4.1, Xcode 26.1.1, iOS 26.0, mitmproxy 12.2.3.

## The question

The Simulator uses the **host Mac's** network stack. The obvious route — editing
macOS network-service settings — is refused outright: it is a system-wide change
whose blast radius is the operator's whole machine, and the consent rule forbids
an agent making it autonomously (N-13). So what is left?

## U-005 — is `simctl keychain add-root-cert` enough for TLS trust?

**Yes, and it is scoped to one simulator.** Confirmed from the tool's own help:

```text
$ xcrun simctl keychain
Manipulate a device's keychain
Usage: simctl keychain <device> <action> [arguments]

    add-root-cert [path]
        Add a certificate to the trusted root store.
    add-cert [path]
        Add a certificate to the keychain.
    reset
        Reset the keychain.
```

`add-root-cert` writes to the **trusted root store**, which is what TLS validation
consults — unlike the iOS device flow, where an installed profile still needs a
manual toggle in Certificate Trust Settings. Nothing on the host is touched.

Implemented behind its own `--install-ca` flag, which is gated separately from
`--i-understand-mitm` because writing to a trust store is a distinct privileged
act. `reset` is the documented way to undo it; detach deliberately does **not**
call it, since removal is itself a trust-store operation needing its own consent.

## U-004 — can a per-process proxy reach the app?

**Partially — the mechanism exists and is reliable; its coverage is client-dependent.**

`simctl launch` documents the channel explicitly:

```text
If you want to set environment variables in the resulting environment, set them
in the calling environment with a SIMCTL_CHILD_ prefix.
```

So `SIMCTL_CHILD_http_proxy=http://127.0.0.1:<port>` reaches the app process.
What honours it:

| Client | Honours proxy env vars | Captured |
| --- | --- | --- |
| Dart / Flutter `HttpClient.findProxyFromEnvironment` | yes | **yes** |
| `curl`, many Swift/ObjC SDKs that wrap it | yes | yes |
| Native `URLSession` | **no** — reads the *system* proxy configuration | **no** |

This is the honest boundary, and it is reported to the caller rather than buried:
`network attach --platform ios` returns a `urlsession_not_covered` warning and
prints the manual Simulator proxy steps for traffic it cannot reach.

## What shipped

`device_proxy_ios.py`, in priority order:

1. inject `http_proxy` / `https_proxy` / `ALL_PROXY` into the session record, which
   `session launch` then applies to every app it starts;
2. seed the trust store via `simctl keychain add-root-cert`, behind `--install-ca`;
3. print exact manual steps plus the `network status` command that verifies them.

`network attach` reports `mode: "automated"` with the mechanism named, and
`attached: "unknown"` — because no traffic has been seen yet. `network status`
only upgrades that to `true` once flows have actually been recorded. The harness
never claims an attachment it has not observed.

## What was *not* verified end to end

Capturing real traffic from an app on the simulator needs an app under test that
makes HTTP calls. None exists in this repository, and system apps (Safari,
Settings) are launched by the OS rather than by `simctl launch`, so the child
environment never reaches them.

Verified instead, on the real machine:

- the CA is generated and readable under session artifacts;
- `simctl keychain add-root-cert` is the correct, simulator-scoped command;
- `SIMCTL_CHILD_*` is the documented and only supported env channel;
- the proxy itself captures, redacts, filters, mocks, and exports correctly — proven
  end to end through a loopback client and a counting origin (see the Android path).

**Open follow-up:** add a tiny Flutter or SwiftUI sample app to the repository that
issues one HTTP request, so this last leg becomes an automated check rather than a
reasoned argument.

## Refused, and why

| Option | Refused because |
| --- | --- |
| `networksetup -setwebproxy` on the host | system-wide network change; forbidden by the consent rule. A static test asserts `networksetup` and `scutil` appear nowhere in the codebase. |
| Binding the proxy to a LAN address so a device can reach it | turns the operator's machine into an open proxy for the duration; also contradicts the loopback-only rule. |
